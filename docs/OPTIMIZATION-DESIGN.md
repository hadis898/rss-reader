# RSS Reader 优化设计文档

## 1. 目标与范围

本文档用于指导 `rss-reader` 的下一阶段迭代，聚焦三类优化：

- UI 界面布局与视觉体验美化
- 后台能力增强（稳定性、性能、可观测性、可扩展性）
- 可新增功能设计（提升用户价值与产品竞争力）

设计原则：

- 保持轻量部署（Docker 单容器优先）
- 兼容当前配置方式（`config.json` 热更新能力保留）
- 演进式改造，避免一次性大重构导致不稳定

## 2. 当前现状评估

结合现有代码与配置，项目当前具备：

- 基础 RSS 聚合读取
- 周期拉取与内存缓存
- WebSocket 增量推送
- 夜间模式与响应式布局
- `config.json` 热更新

主要问题与瓶颈：

- 前端 UI 信息密度高，但层次感与可操作性不足（缺少筛选、排序、搜索、已读管理）
- WebSocket 生命周期管理较弱（心跳与重连逻辑较粗放）
- 后端仅内存缓存，服务重启后状态丢失
- 缺少健康检查、指标监控、错误告警等运维能力
- 配置项语义较少，不支持按源粒度控制（超时、分类、开关等）

## 3. UI/UX 优化设计

## 3.1 页面信息架构重构

从“纯卡片瀑布流”升级为“三段式布局”：

- 顶部导航栏：品牌、全局搜索、主题切换、刷新状态
- 左侧筛选面板（移动端抽屉）：来源分类、更新时间、关键词过滤
- 主内容区：Feed 卡片列表 + 文章列表（支持列表/紧凑两种视图）

核心收益：

- 降低扫描成本，快速定位感兴趣内容
- 提升多源场景下的可控性

## 3.2 视觉风格与组件规范

- 统一间距体系（8px 栅格），卡片圆角、阴影、边框统一
- 标题/正文/辅助信息建立字号层级（例如 16/14/12）
- 夜间模式升级为“主题系统”：
  - `light` / `dark` / `system` 三态
  - 支持跟随系统切换
- 支持来源 favicon 显示，提升识别速度

建议补充样式变量（CSS Variables）：

- `--bg-primary`, `--bg-card`, `--text-primary`, `--text-secondary`
- `--accent`, `--border-color`, `--shadow-sm`, `--radius-md`

## 3.3 交互能力增强

- Feed 内文章支持：
  - 关键词高亮
  - 一键标记已读 / 全部已读
  - “仅看未读”过滤
- 列表排序支持：
  - 按发布时间（如果 RSS 提供）
  - 按抓取更新时间
  - 按来源名称
- 可选“自动滚动到最新”与“固定阅读位置”

## 3.4 前端技术建议

考虑两种路线：

- 路线 A（低成本）：继续使用当前 Vue + Element Plus 静态资源模式，分离 `index.html` 内联脚本为模块文件，逐步组件化
- 路线 B（中长期）：迁移到 Vite + Vue3 + TypeScript，建立工程化能力（lint/format/test/build）

优先建议：先落地路线 A，保障快速上线；后续视团队精力切路线 B。

## 4. 后台能力优化设计

## 4.1 拉取与更新机制

当前问题：固定间隔全量轮询，错误重试与超时控制有限。

优化方案：

- 每个源独立调度（worker pool + context timeout）
- 支持指数退避重试（网络错误/5xx）
- 支持源级配置：
  - `enabled`
  - `interval`
  - `timeoutSec`
  - `maxItems`
- 对比策略从“仅首条 link”升级为：
  - item guid/link + pubDate hash 去重
  - 增量集合合并，避免误判

## 4.2 数据存储与状态管理

新增持久化层（按迭代分级）：

- P0：保持内存缓存（现状）
- P1：引入 BoltDB/SQLite 持久化 Feed 结果和已读状态
- P2：支持多用户时再考虑 PostgreSQL

建议存储内容：

- Feed 元数据（title/link/last_success_time/error_count）
- Item 元数据（guid/link/title/pub_time/summary/hash）
- 阅读状态（read/starred/archived）

## 4.3 WebSocket 与 API 设计

增强点：

- WebSocket 连接管理中心（连接数限制、心跳超时、广播通道）
- 增量消息协议（`type`, `payload`, `ts`）
- 新增 REST API：
  - `GET /api/feeds`
  - `GET /api/items?feed=&keyword=&unread=1`
  - `POST /api/items/read`
  - `POST /api/items/star`
  - `GET /api/health`
  - `GET /api/metrics`（Prometheus 格式）

## 4.4 可观测性与运维

- 日志结构化（JSON），输出 `level`, `feed`, `duration_ms`, `error`
- 增加健康检查：
  - 进程存活
  - 最近一次成功抓取时间阈值
- 增加监控指标：
  - 抓取成功率
  - 单源抓取耗时
  - WebSocket 在线连接数
  - 每分钟推送条目数

## 4.5 安全性

- SSRF 防护（限制可访问协议/内网地址）
- URL 白名单或黑名单策略
- HTTP Client 全局超时与最大重定向次数
- 可选基础鉴权（Basic Auth / Token）保护管理接口

## 4.6 管理员后台设计（新增）

目标：让配置管理从“手动改文件+重启验证”升级为“可视化在线管理+即时生效”。

设计要点：

- 后台页面：`/admin`
- 核心接口：
  - `GET /api/admin/config`：读取当前配置
  - `PUT /api/admin/config`：保存配置并立即重载
  - `POST /api/admin/test-source`：测试单个 RSS 源可用性
- 鉴权：
  - `Authorization: Bearer <token>`
  - `X-Admin-Token: <token>`
  - Token 来源支持 `ADMIN_TOKEN`（环境变量）优先于 `config.json`
- 交互能力：
  - 表单化增删源
  - JSON 预览与双向同步
  - 基础字段校验与错误提示
  - 操作日志面板

后续增强方向：

- 源排序（上移/下移）
- 操作审计日志
- 管理员多角色权限
- 登录会话与过期策略

## 5. 可新增功能清单（按优先级）

## 5.1 P0（1-2 周，立即增值）

- 全局搜索（标题/描述）
- 源分组与筛选
- 已读/未读状态
- 手动刷新单个源
- 错误源标识与重试按钮

## 5.2 P1（2-4 周，提升粘性）

- 收藏与稍后读
- 关键词订阅（命中后置顶或高亮）
- 通知能力（Web Push/邮件/企业微信机器人）
- OPML 导入导出
- 多语言（中文/英文）

## 5.3 P2（中长期）

- 多用户与权限（个人订阅空间）
- 智能摘要（LLM 摘要、去重聚类）
- 热点聚合视图（同主题多源合并）
- 移动端 PWA（离线缓存）

## 6. 配置文件演进建议

建议从当前扁平结构升级为兼容式结构：

```json
{
  "refresh": 6,
  "autoUpdatePush": 7,
  "theme": "system",
  "sources": [
    {
      "name": "知乎",
      "url": "https://www.zhihu.com/rss",
      "enabled": true,
      "interval": 6,
      "timeoutSec": 8,
      "category": "tech",
      "maxItems": 50
    }
  ]
}
```

兼容策略：

- 若检测到旧字段 `values`，自动转换为 `sources`
- 输出警告日志但不中断运行

## 7. 分阶段实施计划

## 7.1 里程碑 M1（第 1 周）

- 前端：布局重构 + 搜索/筛选 + 主题三态 + 管理后台增强
- 后端：`/api/health` + 结构化日志 + 管理员配置接口
- 文档：接口说明与部署说明更新

验收标准：

- 首屏加载时间不劣化
- 移动端可用性明显提升
- 管理员后台可完成“加载-编辑-保存-生效”闭环

## 7.2 里程碑 M2（第 2-3 周）

- 引入持久化（SQLite/BoltDB）
- 已读/收藏状态闭环
- 单源刷新、错误重试、源级配置

验收标准：

- 重启后数据可恢复
- 抓取失败可追踪、可重试

## 7.3 里程碑 M3（第 4 周）

- 指标监控、基础告警
- OPML 导入导出
- 性能调优与压测

验收标准：

- 100+ 源稳定运行
- 关键指标可观测

## 8. 非功能性指标（建议目标）

- 可用性：连续 7 天稳定运行，无崩溃
- 性能：100 个源下，单轮抓取完成 < 90s（取决于源响应）
- 资源：Docker 内存常驻 < 300MB（视条目数量）
- 安全：默认开启超时、重定向限制、SSRF 基础防护

## 9. 风险与应对

- 旧模板与新交互并存带来复杂性  
  应对：先做 API 稳定层，再逐步替换前端视图

- 部分 RSS 源不规范导致解析失败  
  应对：错误隔离 + 单源重试 + 失败降级展示

- 持久化引入后迁移成本上升  
  应对：先抽象 Repository 接口，后切换具体实现

## 10. 推荐下一步（执行顺序）

1. 先做 `API + 数据结构` 统一（为 UI 和持久化打底）
2. 同步推进 `UI 布局重构`（先实现搜索、筛选、主题）
3. 接入 `已读/收藏` 与持久化
4. 补齐 `health/metrics`，最后做压测与文档完善
